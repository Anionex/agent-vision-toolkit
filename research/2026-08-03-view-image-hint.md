# 能否用模型的 reasoning 生成更好的 image hint

2026-08-03 · 离线分析，未消耗 vision 调用

## 问题

代理为每张图生成 focus hint。当前取法：

| 图的来源 | hint |
|---|---|
| 粘贴（`message.content[]`） | 该条 message 自身的文本 |
| 工具取回（`function_call_output.output[]`） | 最近一条 assistant `output_text`，回退到最后一条 user 文本 |

问题出在第二行。`model_reasoning_summary = "none"` 时模型调工具前几乎不输出可见文字，
`output_text` 分支基本走不到，一路回退到 user 文本 —— 于是模型裁出一小块 crop 去看细节时，
hint 仍是整轮任务的描述（"根据截图还原UI为HTML"）。

候选改法：改用紧邻 `function_call` 的 reasoning 文本作为 hint。本文用真实数据检验它。

## 数据

单次会话 rollout `019fc6e7-bca4-7633-b490-4ff2ae0c3442`，任务是"根据截图还原 UI 为 HTML"，
含 **49 次 `view_image` 调用**。取每次调用前最近一条 `reasoning` item（遇 user turn 清空）。

## 结果一：可用性 100%

**49/49 次调用前都有 reasoning，一次不缺。**

`reasoning` item 的 `content[0].reasoning_text` 是明文，`encrypted_content` 为 `null`。
配合 `disable_response_storage = true`（历史每轮全量重发，代理日志中 `images=6→9→12` 单调
增长可佐证），这段文字确实在发给代理的 `input` 数组里。

"reasoning 会被上下文裁剪丢掉"这一风险不成立。

### 绑定关系：隔着一次工具往返

间隔全部 ≤7 项，但 **45/49 中间夹着 `function_call_output`** —— reasoning 和 view_image
不在同一个 assistant turn。最常见的形态：

```
reasoning（"裁这三块来看"）→ exec_command（裁图）→ 输出 → view_image
```

模型是**先想好、再裁、再看**，中间那次裁图的往返不产生新的 reasoning。所以那段 reasoning
确实是这次看图的意图，只是不紧邻 —— 取"最近一条 reasoning"是对的取法。

并行调用共用同一段 reasoning：

```
共用 1 次: 23 段
共用 2 次:  8 段
共用 3 次:  2 段
共用 4 次:  1 段
```

## 结果二：长度是主要障碍

```
min 17   p25 474   中位 1425   p75 2762   max 6478   均值 1753  (字符)

     0-200     9 次  █████████
   200-500     3 次  ███
   500-1000    9 次  █████████
  1000-2000    9 次  █████████
  2000-4000   14 次  ██████████████
  4000-∞       5 次  █████
```

整段直接当 hint 不可行 —— 中位 1425 字、四成超过 2000 字，塞进 vision prompt 会稀释描述目标。
必须截取。

## 结果三：意图确实在，而且就在结尾

第一版分析在这里判断错了：我截取 reasoning 的**尾部 N 字**，看它在讲什么，得出"29% 跑题"。
但"末尾恰好在讲什么"和"意图在不在"是两个问题。改成按句子扫描整段、定位**最后一句表达看图
意图的句子**（含 看/裁/crop/放大/截图/view_image/图中 等）：

```
45/49  整段中存在看图意图句
 4/49  完全没有

最后一句意图 距 reasoning 结尾的字符距离：
  min=5   p25=33   中位=40   p75=63   max=474

  落在尾 200 字内: 41/49 (84%)
  落在尾 300 字内: 43/49 (88%)
  落在尾 500 字内: 45/49 (92%)
```

**意图不但在，还就在末尾。**提取难度不是障碍 —— 尾 300 字这个最朴素的窗口就能覆盖 88%。

## 结果四：意图有，但几乎没有信息量

读完全部 45 条"最后一句意图"，按"这句话作为 hint 能否让 VLM 比看图本身多知道点什么"分类：

| 性质 | 约 |
|---|---|
| 有内容 —— 点名了要看什么、要回答什么 | 13 |
| **纯程序性 —— 只说"裁一下看看"** | **21** |
| 跑题 —— 查 help、翻旧文件、关于 view_image 的元讨论 | 9 |
| 整段无意图句 | 4 |

程序性的长这样：

```
用 Python PIL 裁剪原图局部放大，然后 view_image 查看。
让我把 4 个区域分成 2 张图分别看。
组合裁剪：
让我先看剩下的裁剪图，然后批量修 HTML，再重新截图 diff。
```

作为 hint 等于没给 —— "裁这块来看"里的"这块"就是图本身，VLM 已经拿到了。

有内容的只有约 13 条，但确实好：

```
[19] 卡片1 图标: x 560..830, y 430..560（看是否有浅蓝背景方块）
[31] 让我直接看原图侧边栏裁图（x 20-253, y 170-620）让 vision 直接转录每行文本和位置
[39] 再看行 1 的 toggle/箭头按钮确切位置：裁剪 y 0-45 看
[38] 让我看 x=60 处 y 140-200 的详细颜色
```

原因是结构性的，模型自己说破了：**它把意图编码进裁剪框，不编码进文字。**裁剪框是它唯一的
通道，一个没人听得见的问题，它没有理由说出口。

### 附带的 1:N 问题

11/49 的调用与兄弟调用共用同一段 reasoning，而那段 reasoning 描述的是**全部**兄弟。
`[22][23]` 的结尾：

```
组合裁剪：
1. cards 完整 (415,415)-(1220,615)
2. fullaccess 图标 (440,725)-(575,765) 4x
3. 发送按钮 (1140,715)-(1235,770) 4x
4. 模型选择器文本 (960,730)-(1180,755) 4x
```

两张图会拿到同一条罗列 4 个区域的 hint，对各自都有一半是错的。而恰恰是这类"一次想好裁 N 块"
的场景里，意图内容最丰富 —— 想要的和能路由的正好相反。

## 结果五：文件名过滤器不成立

设想用"reasoning 提到该图文件名"来判定相关性。实测 **7/49**。

原因同上：模型先规划裁剪区域，再在后续 exec_command 里创建文件，最后才 view_image。
规划时写的是坐标和元素名，不是将来的文件名。这个过滤器筛掉的恰好是最优质的那批 hint
（`[19]` 的四点裁剪计划、`[31]` 的逐行转录要求全部落选）。

放宽成关键词（尾 400 字含 裁/crop/放大/截图/看图）则留下 41/49，跑题的那批大多也提到
"截图/对比图"，挡不住。两者交集 7/49。

## 模型自述

`[46]-[49]` 那段 reasoning 里，模型自己诊断了这个问题：

> view_image 的"焦点"由裁剪框决定，不由我的意图决定；**我的意图和它的输出之间没有通信渠道**。
> 当裁剪框里有多个元素时，它优先描述什么是我控制不了的。
>
> 如果我裁剪 x80-200 但心里想的是"绿点右边的元素"，vision 不会知道我想看绿点右边，
> 它只会从头开始描述。

它的代偿是把裁剪框收紧到只剩目标 —— 49 次调用绝大多数是很紧的 crop。代偿有效但昂贵：
`[15][16][17]` 连续三次都在重调同一个 Full access 图标的裁剪框。

需要注意：本次会话中模型并不知道 `glance` 存在（该会话开始于工具说明被移出 system prompt 之后）。
显式的意图通道本来就有，它只是没有。这 49 次调用的挣扎有多少属于工具知识缺失、多少属于机制缺陷，
本数据无法拆分。

## 结论

1. **可用性不是问题**：49/49 有 reasoning，45/49 含明确看图意图，且 88% 落在尾 300 字内。
   "拿不到"和"提取难"都不成立。
2. **信息量才是问题**：约 21/49 的意图是纯程序性的（"裁一下看看"），作为 hint 相对图本身
   零增量；约 13/49 才带内容。投入产出比撑不起改动。
3. **1:N 路由无解**：11/49 与兄弟调用共用 reasoning，而意图最丰富的恰恰是这类"一次想好裁
   N 块"的场景 —— 想要的和能路由的正好相反。
4. **`output_text` 分支应当删除** —— 49 次里一次都没派上用场，而它承担着跑题风险。
5. **两条路通向同一个动作。** 模型不把意图写成文字，是因为没有能听见文字的通道；
   一旦它知道 `glance -q "<问题>"` 存在，意图就会被说出来 —— 而那时它已经走了显式通道，
   代理不需要再反推。所以无论从"反推不划算"还是从"信号为何缺失"出发，收益最高的动作都是
   **让模型知道这些工具存在**，而不是在代理侧猜。

## 局限

单会话、单任务类型（UI 还原）、单模型。UI 还原任务天然产生大量密集 crop，
其他任务（读报错、看图表）的 reasoning 形态可能完全不同。分类计数含人工判断，不宜外推。

本次会话中模型不知道 `glance` 存在（会话开始于工具说明被移出 system prompt 之后）。
"意图不被说出来"这一现象有多少源于通道缺失，本数据无法与机制缺陷拆分 —— 但这恰好是结论 5
可以证伪的地方：把工具说明放回去，再测一次同类任务，如果意图开始出现在文字里，结论 5 成立。

## 后记：结论 2/3/4 已被后续数据推翻（2026-08-03 晚）

本文只看了单会话 49 次调用。换成 245 个真实 call site 复测后：

- **结论 4 错了。** 「`output_text` 分支一次都没派上用场」是这一个会话的样本假象。
  更大样本里，紧邻 `view_image` 的 assistant 输出有 36% 是 reasoning——分支不该删，
  该补上 reasoning 这条来源。
- **结论 2「信息量撑不起改动」也不成立**，前提是别把整段 reasoning 塞进去。
  整段动辄几千字符（文件列表、放弃的猜想），而 hint 上限 500——"没信息量"其实是
  被噪声稀释了。只取**收尾段落**（模型宣布要看什么的那一句）后，245 个点位有 242 个
  非空，中位数 44 字符。
- 已按此实现，见 `16ceb66`。

仍然成立的是结论 1（可用性）、结论 5（让模型知道工具存在），以及"局限"一节——
单会话样本不足以下这类判断，这次正是被它自己的局限说中。
